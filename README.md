# Care Signals

**A patient-care agent that turns a signed imaging order into a real price comparison, a real message to the patient, and a real appointment — unattended.**

CPT 72148 (MRI, lumbar spine, without contrast) costs **$586** at one San Francisco facility and **$3,387** at another, four minutes and forty-nine miles apart, for the same patient on the same Cigna plan. That data is public — hospitals are legally required to publish it — and completely unreadable in practice. Care Signals parses a signed order, pulls the actual published price files, matches the patient's real plan, computes what she actually pays, cites every dollar to its source, texts her the options on WhatsApp, and books the cheapest one — with no clinician follow-up required after the order is signed.

**Live demo:** **https://care-signals-demo.vercel.app**

---

## What it does

1. **Reads a signed order** (`demo_encounter.json`) — a synthetic primary-care encounter: ambient transcript, generated clinical note (HPI / Assessment & Plan), and a signed order for an MRI lumbar spine without contrast.
2. **Parses the order to CPT 72148** and matches it against a cached price dataset pulled from real hospital machine-readable files (MRFs) and a live cash-price page — see [`data_card.md`](data_card.md) for full provenance, every source URL, and every data-quality caveat.
3. **Matches the patient's real insurance plan** (Cigna, high-deductible) against each facility's negotiated rate where one exists, falling back to the cash price where it doesn't — and says so explicitly. Nothing is ever invented; a missing rate renders as `"not published"`, never a blank or a guess.
4. **Computes out-of-pocket cost** (deductible portion + coinsurance portion) per facility, with the arithmetic shown, not just the answer.
5. **Texts the patient the options on WhatsApp** (real Twilio send, not simulated) and, on reply, answers her questions with Claude — grounded strictly in the same cached facility data, never inventing a price or a fact.
6. **Books the recommended facility** and generates a real, downloadable `.ics` calendar file with a reminder 3 days ahead.

## The two-page demo flow

| Page | What it shows |
|---|---|
| **`encounter.html`** — clinical surface | Patient context strip, the generated note as the hero (HPI → Assessment & Plan → signed order), ambient transcript collapsed behind a disclosure. A "Care Navigator" sidebar with one primary action: **"Run care navigation on this order."** Clicking it is the *only* input required — it navigates to page 2 and starts the run automatically. |
| **`navigation.html`** — care navigation | A live, timestamped terminal streams the agent's five steps (parse order → CPT, fetch + filter each facility's real published file, match the plan, compute OOP, attach citations) with real file sizes and match counts. The price cards populate one at a time as each facility resolves. Once all four are priced, the patient-message beat appears automatically; the **one presenter-controlled action** is sending that message via the real Twilio WhatsApp integration. Then: booking confirmation, reminder, and the `.ics` download. |

Everything computed on these pages — every price, every citation, every out-of-pocket figure — comes from `agent_output.js` / `encounter_output.js`, both generated by `agent.js` from the source data files. Nothing is hardcoded in the HTML.

## Architecture

```
demo_encounter.json  ─┐
prices_72148.json     ├──► agent.js ──► agent_output.js       (per-facility rates, OOP, citations)
oop_scenarios.json   ─┘              └─► encounter_output.js  (patient / encounter fixture)

encounter.html ──navigate──► navigation.html
   (both load agent_output.js + encounter_output.js + demo.js + demo.css + sms-text.js)

navigation.html ──POST /send──► server.js ──► Twilio (WhatsApp) ──► patient's phone
patient's reply ──Twilio webhook──► server.js ──► Claude (grounded in the same cached facility data) ──► Twilio ──► reply
```

- **`agent.js`** — the actual pricing agent. Parses the signed order to a CPT code, matches the patient's payer against cached facility rates, computes deductible + coinsurance, attaches a source citation to every figure, and writes the two generated files below. Run it any time the source data changes: `node agent.js`.
- **`agent_output.js`** / **`encounter_output.js`** — generated, not hand-edited. Loaded directly into both HTML pages via `<script src>`.
- **`demo.js`** / **`demo.css`** — shared rendering logic and styles for both pages (card markup, `.ics` generation, sorting, the assistant-panel copy) so the two pages can never drift out of sync with each other.
- **`sms-text.js`** — builds the patient-facing message text. Shared verbatim between the browser (mock preview) and `server.js` (the real send), so the simulated and live messages are guaranteed identical.
- **`server.js`** — Express server with two routes:
  - `POST /send` — sends the options message to the patient over Twilio WhatsApp.
  - `POST /webhook` — Twilio's inbound-message webhook. Calls Claude with the full facility dataset as grounding and replies on the same thread, with short-lived per-sender conversation memory so it doesn't re-ask questions the patient already answered.
- **`prices_72148.json`** / **`oop_scenarios.json`** / **`data_card.md`** — the underlying price dataset, out-of-pocket model, and full data provenance/citations. This is real data pulled from real hospital MRFs and a live cash-price page — see `data_card.md` for the exact source of every number and every gap.
- **`voiceover.js`** / **`voiceover_script.txt`** — generates the demo voiceover via Cartesia TTS (optional, not required to run the app).
- **`options_card.html`** / **`options_card_v1.html`** — earlier single-page versions of the demo, kept for reference; the current demo is the two-page flow above.

## Running it

### Frontend only (what's on Vercel)

The two-page demo is fully static — everything except the real WhatsApp send and Claude replies works from a plain static file server or `file://`:

```bash
open encounter.html
```

or serve the repo root with any static server. The Vercel deployment (`https://care-signals-demo.vercel.app`) is exactly this: a static copy of `encounter.html`, `navigation.html`, `demo.css`, `demo.js`, `sms-text.js`, and the two generated data files. On that hosted link, the "send" button shows a clear preview of the exact message instead of attempting a live send, since there's no backend there to send it.

### Full stack, including the real WhatsApp send

The live send/reply loop needs `server.js` running somewhere Twilio can reach it:

```bash
npm install
cp .env.example .env   # fill in real Twilio + Anthropic credentials
node agent.js          # (re)generate agent_output.js / encounter_output.js
node server.js         # starts on PORT (default 3000)
```

Then open `http://localhost:3000/encounter.html` (served by the same Express app via `express.static`) and register your public URL as the Twilio number's inbound webhook (`/webhook`). Locally, that public URL comes from a tunnel like `ngrok http 3000`.

## ⚠️ Deploying `server.js` for production: use Railway, not Vercel

**The Vercel deployment linked above is intentionally a static-only build.** Vercel's default serverless model doesn't fit `server.js` as written — it holds short-lived, in-process conversation history per patient (`server.js`'s `conversations` map) across separate inbound Twilio webhook calls, and expects to run as one long-lived process, not a cold-started function per request. Running it on Vercel would silently drop that conversation memory between messages and reintroduce the repeated-question bug the memory fix was built to solve.

**Railway** (or any other always-on Node host — Render, Fly.io, a plain VM) is the right target for `server.js` in production:

1. Create a new Railway project from this GitHub repo.
2. Set the start command to `node server.js` (Railway auto-detects `package.json`'s `start` script, so this should already work).
3. Add the environment variables from `.env.example` in Railway's dashboard — **never commit `.env`**.
4. Railway gives you a stable public HTTPS URL — register `https://<your-railway-app>/webhook` as the Twilio number's inbound messaging webhook (replacing the temporary ngrok URL used for local dev).
5. Point the "Send to patient (live)" flow at that same Railway URL instead of `localhost:3000` if you want the *hosted* Vercel frontend to be able to trigger a real send too (currently the hosted frontend only previews the message, per the note above — wiring it to a public backend URL is a small follow-up, not yet done).

## Data integrity

Every dollar figure in this project traces to a real, cited source — see `data_card.md` for the full audit trail, including facilities where a rate genuinely isn't published (rendered as `"not published"`, never guessed) and every schema quirk encountered while pulling the source files. `demo_encounter.json` is entirely synthetic: a fictional patient, fictional clinician, no real PHI — see the `_disclaimer` field in that file and the banner on both demo pages.

## Credentials

All credentials are environment-only, loaded from `.env` (gitignored, never committed) via `.env.example` as the template: Twilio (SMS/WhatsApp), Anthropic (Claude replies + the pricing model), and optionally Cartesia (voiceover generation only). If you're auditing this repo, `.env` has never been committed at any point in its history.
